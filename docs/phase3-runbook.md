# 演示操作顺序

1. 按 README 启动 api/worker。管理员登录可见 6 案，打开负库存案件，展开证据查看 snapshot/batch 引用与库存事实。
2. 提交“正常结构化诊断”，观察任务状态和新任务对应结果。completed 表示诊断保存，案件仍需人工核实，不表示库存已修复。
3. 同案提交“证据不足”，结果为 blocked 且带缺口说明。提交“未知引用”或“格式错误”，任务失败，不能产生新结论；保留的有效结果带有其任务编号。
4. 提交“超时”，等待最多两次执行后失败。每次执行预留一次 Mock 策略额度，没有真实模型费用。
5. 切换东仓账号，应只见 4 案；只读账号不能诊断/复检，直接调用 API 也被拒绝。退出清空旧案件与结果。

## 可靠性复现

`demo/run_checks.py` 使用专用临时 PostgreSQL（本机 25435），与演示库 25434 分开。只操作自己启动的子进程。

- SIGKILL：等第一代领取后强制结束，等待真实租约过期，再启动新进程以第二代完成。
- SIGSTOP/SIGCONT：第一代取得有效 Provider 结果后暂停整个进程，心跳一同停止；第二代接管完成，再恢复第一代，验证返回 lease_lost 且新结果 request_id 不变。
- 正常长执行：心跳跨过初始租约期限，其他 Worker 不能接管。

任务 ID、持有者、代次和终态保存在 `runtime/test-evidence/`。测试为 0.9 秒租约/0.1 秒心跳；交互演示为 6 秒租约/1 秒心跳，均标为演示配置，不冒充源生产值。

已有工作流时种子脚本保留运行状态。完全恢复样本可先停应用，删除本候选专用数据卷，再重新启动。测试夹具还要求专用端口和显式测试标记，原业务库与阶段二环境不参与。
